# 승인 처리 결과

**승인의 실제 결과는 같은 턴에 입력 훅이 넣은 `[Vibe Refactor 승인 처리 결과 — 입력 훅]` 블록이다.** 사용자가 입력창에 `/refactor:approve` 를 치면 입력 훅이 승인 스크립트를 실행해 `APPROVALS.log`에 단계 ID와 카드 지문(그 순간의 카드 내용)을 기록하고 계획서의 승인 칸·STATE를 바꾼다. 그 블록을 기준으로 사용자에게 3~6줄로 전한다. 승인 뒤 카드 내용이 바뀌면 그 승인은 풀린다는 것을 한 줄로 알려 준다.

아래 `!` 출력은 처리 전 현황일 수 있다(스킬의 명령은 입력 훅보다 먼저 돌고, 아무것도 바꾸지 않는다). **그 블록이 없으면 안전장치 훅이 꺼졌거나 시간 안에 끝나지 못한 것이다 — 승인됐다고도, 안 됐다고도 단정하지 말고, `/refactor:approve`(인자 없이)로 현황을 다시 확인하고 `/hooks` 에서 refactor 훅을 확인하라고 안내한다.**

```!
bash "${CLAUDE_SKILL_DIR}/../../hooks/run.sh" refactor-approve "${CLAUDE_PROJECT_DIR}" <<'VIBE_REFACTOR_ARGS'
$ARGUMENTS
VIBE_REFACTOR_ARGS
```

## 너의 할 일 (짧게)

1. 입력 훅 블록의 결과를 비개발자가 알아듣게 3~6줄로 전한다: 무엇이 승인·취소됐는지, 다음에 입력할 명령.
   - 마무리 결과를 전할 때 "안전장치가 모두 꺼집니다(비밀값·되돌릴 수 없는 명령 보호 포함)"는 줄이지 말고 그대로 전한다.
2. **👤 사람이 직접 할 일**이 "없음"이 아닌 단계가 있으면 맨 위에 굵게 적는다. 그중 단계 실행 **전에** 끝나야 하는 것(예: 결제사 테스트 키 발급, DB 백업 확인, 비공개 저장소 만들기)은 "이것부터 해 주세요"라고 먼저 말한다.
3. 다음 명령 안내:
   - 실행 대기(승인됨) 단계가 있으면 → `/refactor:go` (승인된 단계를 차례로 이어서 실행하고, 멈출 일이 생기면 멈춘다 — 한 단계씩 보려면 `/refactor:go 하나씩`)
   - 기준선 계획을 승인했으면 → `/refactor:go` (기준선 테스트를 만들고 커밋한 뒤 결과를 보고한다)
   - 승인 대기만 남았으면 → 계획서 `docs/refactor/REFACTOR_PLAN.md`를 보고 `/refactor:approve <단계ID>`
   - 승인한 카드에 "🔓 고칠 기준선" 줄이 있으면 → 그 단계의 기준선 허용이 **승인과 함께 열렸다**고 전한다(따로 `허용`을 칠 필요 없음). 그 단계를 실행하는 동안만 열리고 끝나면 저절로 닫힌다는 것, 닫으려면 `/refactor:approve 허용 닫기`.
   - 승인한 카드에 "⚠️ 🛠 카드가 아니라 기준선 허용을 자동으로 열지 않았습니다" 줄이 있으면 → 저절로 열리는 것은 🛠(동작이 바뀌는) 카드뿐이라 열지 않았다고 전하고, 그 카드가 정말 기준선을 고쳐야 하는지 계획서를 확인하라고 한다(필요하면 사용자가 `/refactor:approve 허용 <ID>`).
4. **허용 결과**(`🔓 기준선 허용: …` — `허용` 명령의 결과든 승인과 함께 열린 것이든)를 전할 때: 어느 단계가 어떤 기준선 파일을 고칠 수 있게 됐는지, 그 단계를 실행하는 동안만 열리고 단계가 모두 끝나면 저절로 닫힌다는 것, 다음은 `/refactor:go`. 닫고 싶으면 `/refactor:approve 허용 닫기`. 보류(`보류 <ID>`)한 단계가 허용에서도 빠졌다고 결과 블록에 나오면 그것도 전한다.
5. **push 허락**: 결과 블록에 `✅ push 허락:` 이 있으면 **이번 턴에** 그 줄에 적힌 명령(`git push -u origin <가지>`)을 Bash 도구로 실행하고 결과를 전한다(허락은 이번 차례에만 — 다음 입력부터 다시 막힌다). 결과 블록의 "올라갈 커밋" 목록과 "커밋 안 된 변경" 경고도 함께 전한다. 다른 옵션·다른 가지·다른 원격을 붙이지 않는다. 실패하면 다시 시도하지 않는다: **안전장치(`[refactor 안전장치]`)에 막혔을 때만**(30분이 지남 등) "`/refactor:approve 푸시` 를 다시 쳐 주세요"라고 안내하고, 인증·네트워크·원격 거절(non-fast-forward 등)·샌드박스 오류는 오류 문구를 그대로 전한다(다시 치라고 하지 않는다). 그 뒤 PR 만들기는 사용자가 부탁하면 한다(PR 을 만들었으면 사용자가 입력창에 `/refactor:approve 합치기` — 자동 검사는 스크립트가 기다린다).
6. **새 가지 결과**: 결과 블록에 새 작업 가지를 만들었다는 줄이 있으면 새 가지 이름·어디서 만들었는지·지난 가지는 그대로 남아 있다는 것·따라온 커밋 안 된 변경(있으면)을 전하고, 다음은 `/refactor:go`. 거절됐으면 까닭을 쉽게 전한다. 그중 **지금 가지의 내용이 아직 origin 의 기본 가지에 다 들어 있지 않다**는 거절이면:
   - **이번 턴에** `git fetch origin` 을 한 번 실행한다(받아 오기 — 안전장치가 통과시킨다. 그 밖의 수정·실행은 하지 않는다).
   - 받아 온 뒤에는 늘 "최신 내용을 받아 왔습니다 — `/refactor:approve 새 가지` 를 다시 입력해 주세요(받아 온 내용으로 다시 판정합니다)"라고 전한다. `git log`·`git diff` 로 "PR 이 안 합쳐진 것 같다"고 짐작하지 않는다(rebase·스쿼시로 합치면 커밋 번호가 달라 커밋이 남아 보인다 — 판정은 승인 스크립트가 한다). 다시 쳐도 같은 거절이면 PR 이 아직 안 합쳐진 것이니, PR 이 열려 있으면 `/refactor:approve 합치기` 를 알려 준다.
   - 거절 까닭이 **판정하지 못했다**(❓ … 판정하지 못했습니다)이면 위처럼 받아 온 뒤 다시 입력해 보라고 하고, 그래도 같으면 결과 블록에 나온 터미널 명령(`git switch -c <이름> origin/<기본 가지>`)을 PR 이 합쳐진 것을 사람이 확인한 뒤 **사람의 터미널 꼴로**(「사람에게 주는 명령」 규칙 — WSL·Windows 면 그에 맞게) 전한다. Claude 가 그 명령을 실행하지 않는다(안전장치가 막는다).
7. **합치기 결과**: 입력 훅은 합치기를 **허락만** 한다(인터넷에 닿지 않음). 결과 블록에 `✅ 합치기 허락:` 이 있으면 **이번 턴에** 그 블록에 적힌 명령(`bash "<플러그인>/hooks/run.sh" refactor-merge "<프로젝트 폴더>" <세션ID>`)을 Bash 도구로 **그대로** 실행한다(다른 것을 붙이지 않는다 — 앞에 `cd`, 뒤에 `| tail`·`; echo` 도 붙이지 않는다). **배경 실행(`run_in_background`)으로 돌리지 않는다** — 전경에서 결과를 받는다(허락이 사라졌는지 스크립트가 합치기 직전에 다시 보기 때문에, 배경이면 그 결과를 늦게 안다). 그 스크립트가 PR 을 확인하고 조건이 맞으면 합친다. 출력에 따라:
   - 결과 블록의 30분 경고를 줄이지 말고 그대로 전한다: `⚠️ 허락한 뒤 최대 30분 사이에는 사람이 보고 있지 않아도 조건이 맞으면 합쳐지고 운영 배포가 시작될 수 있습니다 — 멈추려면 아무 말이나 입력하세요 — Claude 가 실행 중이면 먼저 Esc 를 누르세요(Esc 없이 입력만 하면 지금 도는 확인 한 번이 끝난 뒤, 최대 약 2분 뒤에 허락이 끝납니다).`
   - **"같은 명령을 그대로 다시 실행하세요"**가 나오면(⏳ 자동 검사가 아직 도는 중·검사 목록이 바뀜·한 번 더 확인·GitHub 가 아직 계산 중·검사가 아직 등록되지 않음, ⚠️ PR 조회·비교 실패 등) **같은 명령을 다시 실행한다** — 자동 검사가 끝날 때까지 되풀이한다(허락은 그 사이 그대로다). 되풀이할 때마다 사용자에게 한 줄로 진행을 알린다. **되풀이 도중 사용자의 새 말이 오면 되풀이를 멈추고** 그 말에 먼저 답한다(새 말이 오면 허락이 끝난다 — 다시 합치려면 사용자가 `/refactor:approve 합치기` 를 다시). **같은 ⚠️ 가 3번 이어지면 멈추고**(조회·비교 실패뿐 아니라 임시 폴더 실패 등 모든 ⚠️) 오류 문구를 그대로 전한다(네트워크가 막힌 환경일 수 있다 — 사람이 GitHub 화면에서 합치거나, 나중에 `/refactor:approve 합치기` 를 다시).
   - `✅ 합쳤습니다`(또는 `ℹ️ … 이미 합쳐져 있습니다`)면 어느 PR 을 어떤 방식으로 합쳤는지 전하고, "기본 가지에 합쳐지면 운영 배포가 시작될 수 있다"는 경고를 줄이지 말고 그대로 전한 뒤 배포 확인을 제안한다(사용자가 부탁하면 읽기 명령만 — 예: `gh pr view`·`gh run list`). 다음 묶음은 `/refactor:approve 새 가지`.
   - `⛔`·`❓` 거절이면 까닭과 할 일(먼저 `/refactor:approve 푸시` · Claude 에게 "작업 가지 최신 내용 받아 와" 뒤 다시 `/refactor:approve 합치기` · 사람이 GitHub 화면에서 등)을 쉽게 전하고 **다시 실행하지 않는다**(허락이 끝났다).
     - `⛔ PR #… 은 이미 합쳐진 PR 입니다`면 합쳤다고 전하지 않는다. 이미 합쳐진 PR 이면 — 합친 뒤 올린 새 커밋이 있다는 뜻이다: 먼저 `/refactor:approve 푸시` → 새 PR(`gh pr create`) → 기본 가지에 합친 커밋이 있어 '새 커밋 N개' 거절이 나오면 GitHub PR 화면의 Update branch → 검사가 다시 초록 → Claude 에게 "작업 가지 최신 내용 받아 와" → 다시 `/refactor:approve 합치기`. 번호를 잘못 줬으면 번호 확인.
     - `⛔ 합치기 허락이 승인 기록과 맞지 않습니다`·`⛔ 허락이 사라졌거나 바뀌었습니다`(끝 줄이 "허락은 끝났습니다")면 사용자에게 `/refactor:approve 합치기` 를 다시 입력해 달라고 한다. 끝 줄이 "새 허락은 그대로입니다"면 사용자가 방금 새로 허락한 것이니, 이번 차례의 새 결과 블록에 적힌 명령을 그대로 한 번 실행한다.
   - `ℹ️ 이미 마무리되어 안전장치가 꺼져 있습니다`면 **합친 것이 아니다** — 리팩토링이 마무리되어 평소처럼 합칠 수 있다는 뜻이다. 합쳤다고 전하지 말고 그렇게 전한다.
   - 실행이 **안전장치(`[refactor 안전장치]`)에 막혔으면**: 안내에 "아래 꼴 그대로 한 번만 다시 실행"이 있으면 명령을 고치지 말고 안내에 적힌 꼴 그대로 **한 번만** 다시 실행한다(그래도 막히면 더 실행하지 않고 아래처럼 다시 입력을 부탁한다). 그 밖(30분이 지남·허락 없음 등)이면 명령을 고쳐 다시 시도하지 말고 "`/refactor:approve 합치기` 를 다시 입력해 주세요"라고 안내한다.
   - **"합쳐졌는지 알 수 없습니다"**(합치기 요청이 시간 안에 끝나지 않음)면 합쳐졌다고도 안 됐다고도 단정하지 말고, `gh pr view <번호> --json state,mergedAt` 로 실제 상태를 읽어 전한다. 합쳐졌으면 위처럼 배포 경고와 배포 확인 제안을 한다.
   - 입력 훅이 허락을 만들지 않았으면(`… 합치기 허락을 만들지 않았습니다`) 그 까닭을 전한다. 방식이 없어 거절됐으면 방식을 붙인 입력 예(`/refactor:approve 합치기 rebase`)를 보여 준다.
   - **합친 뒤 배포가 깨졌다고 하면**: 되돌리기는 사람이 한다 — ① 호스팅 화면(Vercel·Cloudflare·Railway 등)에서 이전 배포로 되돌리기(가장 빠름) ② 코드를 되돌리려면 GitHub PR 화면의 Revert 버튼으로 되돌리는 PR 을 만들고 사람이 GitHub 화면에서 합친다(`/refactor:approve 합치기` 는 지금 작업 가지의 PR 만 받는다) ③ 리팩토링 중에는 Claude 의 배포·되돌리기 명령(`vercel rollback`·`wrangler rollback`·`railway redeploy`·`heroku rollback`·`netlify rollback` 등)을 안전장치가 막는다 — Claude 는 읽기 확인만 한다. ④ Revert PR 을 합친 뒤에는 `/refactor:approve 새 가지` 가 "승인 기록이 지금 가지와 다릅니다"로 거절한다(Revert 가 승인 기록까지 되돌리므로) — 같은 작업 가지에서 고쳐 커밋 → `/refactor:approve 푸시` → 새 PR(`gh pr create`) → '새 커밋 N개' 거절이면 위의 Update branch 순서 → `/refactor:approve 합치기` 로 잇는다.
8. 결과에 ❓가 있으면 무엇이 문제인지 쉽게 설명하고 올바른 입력 예를 하나 보여 준다.
9. **이번 답변에서는 (위 5의 push·6의 `git fetch origin`·7의 합치기 명령·7의 읽기 명령 말고는) 아무 파일도 고치지 말고, 단계 실행도 시작하지 마라.** 실행은 사용자가 `/refactor:go`를 입력할 때 한다.
