# 정밀 점검표: 결제·주문 흐름 (돈이 새는 곳)

온라인으로 돈을 받는 서비스의 대표 사고 세 가지 — ① 화면이 보낸 금액을 서버가 믿어 10만 원짜리가 1,000원에 팔림 ② 결제는 됐는데 주문이 저장되지 않음 ③ 결제사 알림이 두 번 와서 주문·발주·문자가 두 번 나감. 셋 다 에러 없이 조용히 일어난다.

## 이 점검의 안전 규칙
- 결제·취소·환불·웹훅·발송 API를 호출하지 않는다(테스트 키로도). 서버·테스트를 실행하지 않는다.
- 시크릿 키·카드·계좌 정보, 실제 주문·고객 데이터는 출력하지 않는다. 결제 로그 파일을 통째로 열지 않는다.
- **결제사 규칙은 기억으로 단정하지 않는다.** 승인 제한 시간, 웹훅 재전송·서명 방식, 금액 검증 방법은 결제사마다 다르다. 확인하지 못하면 "결제사 문서 확인 필요".
- 법·세무·회계 판단 금지.
- 비슷한 결제 경로(일반·간편·정기·가상계좌·관리자 수동 결제)가 여럿이면 **전부** 본다.

## 먼저 파악
결제사(토스페이먼츠·포트원·나이스페이·KG이니시스·Stripe 등)와 결제 방식, 주문 상태 종류와 흐름, 결제 뒤에 일어나는 일(재고·발주·알림·포인트), 테스트 키와 운영 키를 어디서 구분하는지(변수 이름만).

## 돈 흐름 지도 (먼저 그린다)
장바구니 → 금액 계산 → 주문 생성 → 결제창 → 결제 승인 → 결제사 알림(웹훅) → 주문 확정 → 발주·알림 → (취소·환불)
화살표마다 **브라우저 / 서버**와 **파일:줄**. 브라우저에서 일어나면 안 되는 일이 브라우저에 있으면 표시한다.

## 점검 항목
- **PA1 금액은 서버가 정하나** — 상품가·옵션·수량·쿠폰·적립금·배송비를 서버가 DB 값으로 **다시 계산**하나? 화면이 보낸 합계를 그대로 쓰면 🔴.
- **PA2 결제 전 주문 기록** — 결제창을 열기 전에 서버가 주문번호와 금액을 먼저 저장하나?
- **PA3 금액 대조** — 결제사가 정한 방식 중 하나로(승인 전 돌려받은 금액 대조 / 금액 사전 등록 / 결제 직후 서버가 결제사에 다시 조회해 다르면 취소) 서버 저장 금액과 실제 결제 금액을 확인하나? 확인 방식이 하나도 없으면 🔴.
- **PA4 결제사 알림(웹훅)** — 진짜 결제사가 보낸 것인지 확인하나(서명 또는 재조회)? 같은 알림을 두 번 받아도 한 번만 처리하나(결제 고유 번호로 중복 확인)? 오래 걸리는 일은 응답 뒤로 미루나?
- **PA5 결제됐는데 주문 없음** — 승인 뒤 주문 저장·재고·발주 중 하나가 실패하면? 자동 취소·재시도·알림 중 하나라도 있나, 에러를 삼키고 "주문 완료"를 보여 주나?
- **PA6 중복 제출** — 버튼 연타·새로고침·뒤로 가기로 주문·결제가 두 번 생기나? 버튼 잠금과 서버 쪽 중복 방지가 둘 다 있나?
- **PA7 취소·환불** — 취소 금액을 서버가 계산하나(부분 취소 포함)? 본인·관리자만 취소하나? 상태·재고·알림이 맞게 바뀌나?
- **PA8 주문 상태는 한 곳에서** — 상태를 바꾸는 코드가 흩어져 있나? 있을 수 없는 이동(배송완료 → 결제대기)을 막나?
- **PA9 키 분리** — 개발 환경에 운영 결제 키, 운영에 테스트 키가 들어갈 수 있나? 시크릿 키가 브라우저에 있나?
- **PA10 돈 관련 알림** — 금액 불일치·승인 실패·웹훅 처리 실패가 운영자에게 알림으로 오나? 로그에만 남으면 🟠.
- **PA11 시간** — 마감·당일 처리·예약을 한국시간으로 계산하나(서버는 보통 UTC)?
- **PA12 금액 계산 중복** — 같은 계산이 화면·서버·관리자·정산에 따로 있어 서로 다를 수 있나?

## 점수 상한
PA1·PA3·PA4 중 하나라도 🔴이면 40점을, PA5가 🔴이면 60점을 넘기지 않는다.
