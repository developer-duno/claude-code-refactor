# 정밀 점검표: 데이터 수집 파이프라인 (조용한 0건·중복·요청 예절·권리 위험)

다른 곳에서 데이터를 가져오는 기능(크롤링·스크래핑·외부 API 수집)은 조용히 망가진다. 상대 사이트 구조가 바뀌면 에러 없이 0건이 저장되고, 매번 전체를 다시 받느라 요청이 폭주해 차단되거나 분쟁이 생기고, 깨진 가격·중복 데이터가 그대로 손님 화면에 올라간다. 국내에서도 다른 회사의 매물 데이터베이스를 반복 복제해 서비스한 업체가 데이터베이스권 침해로 손해배상 판결을 받은 사례가 있다.

## 이 점검의 안전 규칙
- **수집기를 실행하지 않는다. 수집 대상 사이트·API에 요청하지 않는다.** 이미 저장된 샘플 파일만 읽는다.
- **차단 우회 방법을 제안하지 않는다.** IP 돌리기·캡차 우회·로그인 우회·브라우저 위장이 코드에 있으면 🔴로 표시하고, 방향은 "허용된 방식(공식 API·공공데이터·제휴·허락)으로 전환 검토"로 적는다.
- **법률 판단 금지.** 사실(무엇을·어디서·얼마나 자주·어떻게 쓰는지)만 정리하고 "법률 검토 필요"를 붙인다. 대상 사이트의 약관 내용을 기억으로 인용하지 않는다.
- 수집용 계정·쿠키·토큰이 코드에 박혀 있으면 위치만 적고 🔴.
- 속도 문제는 여기서 다루지 않는다(성능 점검표로).

## 수집 지도 (먼저 그린다)
| 대상 | 방법(공식 API / HTML 요청 / 브라우저 자동화) | 주기·실행 위치(크론·GitHub Actions·서버리스·PC) | 코드(파일:줄) | 저장 위치 | 손님 화면에 게시? |

## 점검 항목
- **PI1 수집 근거·권리(사실만)** — 대상별로 공식 API·공공데이터인지, 이용약관·robots.txt를 확인한 기록이 있는지, 가져온 데이터를 그대로 재게시하는지 가공하는지, 출처를 표시하는지. 대량·반복 복제 후 그대로 게시하면 🔴 "법률 검토 필요".
- **PI2 요청 예절** — 요청 사이 간격, 동시 요청 수 상한, 재시도 상한과 점점 길어지는 대기, 한 번에 가져오는 양.
- **PI3 증분 수집** — 매번 전부 다시 받나, 바뀐 것만 받나(수정일·고유 번호 기준)? 받은 것을 캐시하나?
- **PI4 조용한 실패 감지** — 0건·평소보다 급감, 파싱 실패, 로그인·캡차 화면을 정상 데이터로 저장, "응답은 200인데 내용이 비어 있음"을 잡아내나? 작업이 **아예 안 돈 날**(마지막 성공 시각)을 알 수 있나? 이런 일이 생기면 운영자에게 알림이 오나?
- **PI5 품질 검사** — 저장 전에 필수값 누락, 단위(억·만 원, ㎡·평), 이상값(0원·음수·평소의 100배), 글자 깨짐을 거르나?
- **PI6 중복·식별** — 고유 키(출처 + 원본 번호)가 있나? 같은 대상의 다른 표기(주소·이름)를 한 번 정규화해서 비교하나? 저장이 "있으면 갱신, 없으면 추가(upsert)"인가?
- **PI7 원본 보관** — 파싱 버그가 나중에 발견돼도 다시 처리할 수 있게 원본 응답을 기간을 정해 보관하나? (개인정보가 섞이면 최소한으로, 짧게)
- **PI8 변경·삭제 반영** — 가격 변경·거래 완료·판매 종료·원본 삭제가 내 화면에 반영되나? 사라진 매물·상품이 계속 보이면 허위 광고가 될 수 있다.
- **PI9 실행 환경** — 서버리스 시간 제한에 걸려 중간에 끊기지 않나? 같은 작업이 동시에 두 번 도는 걸 막나(잠금)? 개발 중 실행이 운영 DB에 쓰지 않나?
- **PI10 개인정보** — 수집 데이터에 개인의 이름·연락처가 섞이나? 필요한 만큼만, 기간을 정해 두나?
- **PI11 비용** — 지도·주소 변환 같은 유료 API를 같은 값으로 반복 호출하나(캐시 여부)?
- **PI12 시간대** — 수집 시각·원본 수정일이 UTC인지 한국시간인지 코드에서 일관되나?
