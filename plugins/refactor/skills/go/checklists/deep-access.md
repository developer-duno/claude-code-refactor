# 정밀 점검표: 접근 권한 (남의 데이터가 보이나)

AI가 만든 앱에서 가장 흔하고 비싼 구멍은 "로그인은 있는데 누가 무엇을 볼 수 있는지 서버가 확인하지 않는 것"이다. 웹 보안 위험 순위(OWASP Top 10:2025) 1위도 접근 통제 실패다.

## 이 점검의 안전 규칙
- 실제로 시도하지 않는다: 남의 id로 요청 보내기, 서버 호출, 로그인 시도, 토큰 만들기, DB 조회 금지. 코드와 설정 파일만 읽는다.
- 프레임워크 기본 보호를 가정하지 않는다. **실제로 설정된** 미들웨어·가드·정책만 인정한다.
- 대시보드에서만 보이는 설정(Supabase RLS 화면, Firebase 규칙 콘솔, 버킷 공개 여부)은 "사람에게 확인"으로 둔다. 마이그레이션·규칙 파일이 있으면 그걸 읽는다.
- 비슷한 API가 여럿이면 형제 코드를 **전부** 찾는다.

## 먼저 파악
로그인 방식(자체·Supabase Auth·Firebase Auth·NextAuth·소셜), 역할 종류(손님·회원·관리자·파트너), 브라우저가 DB에 직접 붙는지, 사람마다 달라야 하는 데이터(주문·예약·매물·문의·업로드·포인트).

## 점검 항목
- **AC1 관리자 입구** — 관리자 화면과 관리자 API가 서버에서 로그인 + 역할을 확인하나? 버튼 숨김·어려운 주소는 보호가 아니다. 관리자 로그인 시도 횟수 제한이 있나?
- **AC2 남의 것 보기(IDOR = 번호만 바꾸면 남의 데이터가 보이는 구멍)** — id를 받는 모든 조회·수정·삭제 API가 "요청한 사람의 것인지" 서버에서 확인하나? 목록 API가 로그인한 사람 것만 거르나? id가 1, 2, 3처럼 추측 가능한가?
- **AC3 로그인 없이 보는 링크** — 비회원 주문 조회·영수증·공유 링크가 추측할 수 없는 토큰과 만료 기한을 쓰나? 받는 분 전화번호·주소가 그대로 나오나?
- **AC4 DB 행 단위 보안** — (브라우저가 DB에 직접 붙는 경우) 공개 스키마(= 브라우저에서 바로 읽을 수 있는 테이블 묶음, Supabase는 보통 `public`)의 테이블마다 RLS가 켜져 있나? 정책이 `using (true)`처럼 사실상 전체 허용은 아닌가? 쓰기(insert·update·delete) 정책이 따로 있나? Firebase `allow read, write: if true`가 있나? service_role·admin 키가 브라우저 코드나 공개 변수에 있나?
- **AC5 역할 올려치기(대량 할당)** — 가입·프로필 수정·주문 생성 요청 본문을 통째로 저장해서 `role`·`is_admin`·`price`·`point`를 손님이 바꿀 수 있나?
- **AC6 파일 저장소** — 업로드 파일(신분증·계약서·주문 사진 등)이 공개 버킷에 있나? 주소를 추측하거나 목록을 볼 수 있나?
- **AC7 서버 함수·웹훅·예약 작업** — 서버리스 함수·크론·웹훅 주소를 아무나 부를 수 있나? 웹훅은 서명(보낸 곳 확인)을 검사하나?
- **AC8 세션·토큰** — 로그아웃·비밀번호 변경 뒤에도 옛 토큰이 유효한가? 만료 시간이 있나?

## 점수 상한
AC2 또는 AC4가 🔴이면 40점을 넘기지 않는다. ⚪가 3개 이상이면 60점을 넘기지 않는다.
