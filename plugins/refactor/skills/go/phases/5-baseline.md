# 5단계: 기준선 — 현재 동작 사진 찍기 (BASELINE_PLAN → ⏸ G1 → BASELINE)

목표: 고치기 전에 **지금 이 코드가 실제로 어떻게 동작하는지**를 테스트로 고정한다(특성화 테스트·골든마스터). 공사 전에 집 구석구석 사진을 찍어 두는 것과 같다. "원래 이래야 한다"가 아니라 "지금 이렇게 한다"를 기록한다.

★ 테스트부터 쓰는 방식(TDD)과 다르다. TDD는 없는 동작을 먼저 쓰므로 처음엔 빨강이 정상이지만, 기준선은 **있는 동작**을 기록하므로 만들자마자 **초록이 정상**이다. 초록이라고 가짜로 의심해 억지로 깨뜨리지 마라. 버그처럼 보이는 동작도 고치지 않고 "의심 동작"에 적는다.

---

## 1부: 기준선 계획 (BASELINE_PLAN) — 읽기만

1. **테스트 환경 확인**: 테스트 도구·실행 명령·기존 테스트 위치와 개수(정의만). 테스트 설정·코드가 쓰는 DB 주소·키·접속 주소(baseURL)가 개발용인지 **변수 이름으로만** 확인한다(`… refactor-safe-run --check`의 이름 목록을 쓴다). 운영과 구분이 안 되면 계획에 "실행 전 확인 필요"로 적는다.
   - 모든 테스트는 안전 실행기(`… refactor-safe-run -- <명령>`)로 돌린다. 그러면 DB 주소는 `127.0.0.1:9`(접속 즉시 실패), 키는 가짜 값이 된다.
   - PROFILE에 DB가 "하나뿐" 또는 "모름"이면: DB·외부 API를 쓰는 흐름은 "④ 아직 못 찍는 곳"에 "개발용 DB·테스트 키 필요"로 적고, **계산·문구·파싱처럼 DB 없이 도는 부분만** 기준선으로 계획한다. 저장된 샘플(합성 데이터)로 돌리는 골든 파일은 괜찮다.
2. **무엇을 찍을지** (AUDIT_REPORT의 🔴·🟠 흐름부터):
   - ① 돈 계산 — 상품가·옵션·수량·쿠폰·적립금·배송비(지역·시간대별)·수수료: 입력 조합 → 결과 금액 표
   - ② 상태 변경과 메시지 문구 — 주문 상태가 바뀌는 규칙, 알림톡·문자·메일 최종 문자열
   - ③ 수집·정제·매칭 — 저장된 원본 샘플 → 파싱·단위 변환·중복 제거·매칭 결과를 골든 파일로
   - ④ API 응답 모양 — 가짜 요청 → 응답 구조와 핵심 값(시각·id처럼 매번 바뀌는 필드는 제외)
   - ⑤ 핵심 화면 — 스냅샷 도구가 이미 있을 때만
   - ⑥ 성능 기준치(선택) — 로컬에서만, 같은 샘플로 3번 이상 재서 중간값. 운영 부하 측정 금지.
3. **가짜로 바꿀 바깥 호출**: 결제·환불, 알림톡·문자·메일, 운영 DB, 수집 대상 사이트, AI API. 각각 어디서(이음새) 바꿀 수 있는지. 저장된 샘플 응답이 없으면 "샘플 필요"로 적는다.
4. **필요한 개발용 도구와 테스트 설정 파일**: 테스트 도구가 없으면 무엇을 왜 설치해야 하는지(개발 의존성으로만), 새로 만들 테스트 설정 파일(예: `vitest.config.ts`, `jest.config.js`, `conftest.py`, `pytest.ini`, package.json의 test 명령 한 줄)의 이름과 이유.
5. `docs/refactor/BASELINE.md`에 아래 "계획" 부분을 쓴다. 계획 맨 끝에 반드시 이 두 줄을 **줄 맨 앞에서** 넣는다(`기준선 계획 승인:` 줄은 파일에 하나만. 설명 문장이나 표 안에 이 글자를 쓰지 않는다). 사용자가 `/refactor:approve baseline`으로 승인하면 승인 기록(APPROVALS.log)에 남고, 승인은 파일 전체 내용(`## 결과` 제목 앞까지)에 묶인다. 승인 뒤에 계획을 고치면 승인이 풀린다.
   ```
   기준선 계획 승인: [ ]
   껍데기 확인(핵심 줄을 잠깐 바꿔 테스트가 빨강이 되는지 확인): 포함
   ```
6. STATE: `phase: BASELINE_PLAN`, `gate: G1-baseline`, next: "기준선 계획 확인 후 /refactor:approve baseline". **멈추고 보고한다.**

### BASELINE.md 계획 부분 형식
- ① 한 줄 총평(비유) ② 기준선 준비도: 🟢 충분 / 🟠 일부 / 🔴 안전망 없음(🔴이면 "이대로 리팩토링 시작 금지")
- ③ 기존 테스트 현황 `| 위치 | 개수 | 실행 명령 | 결과(아직 실행 전) |`
- ④ 기준선 계획 `| ID | 무엇을 고정 | 대상(파일:줄) | 방식(입출력 표/골든 파일/응답 모양) | 가짜로 바꿀 외부 호출 |`
- ⑤ 아직 못 찍는 곳 `| 영역 | 이유 | 필요한 것 |`
- ⑥ 설치가 필요한 개발 도구와 새로 만들 테스트 설정 파일(이름·이유) — 승인되면 이 목록만 만들거나 고칠 수 있다
- ⑦ 실행 전 확인 필요(테스트 설정이 운영을 가리킬 가능성 등)

## 2부: 기준선 작성 (BASELINE) — 승인 뒤에만

시작 조건: 스킬 맨 위 "지금 상태"에 **"기준선 계획: 승인됨"**이 있어야 한다(체크 표시가 아니라 승인 기록 기준). "승인 대기"나 "승인 뒤 계획 내용이 바뀜"이면 멈추고 `/refactor:approve baseline`을 안내한다.

### 규칙
1. **기존 파일은 고치지 않는다.** 새 파일은 `tests/baseline/`(프로젝트 테스트 폴더 관례가 있으면 그 아래 `baseline/`)과 `docs/refactor/`에만 만든다. 예외 세 가지: ① 껍데기 확인을 위해 한 줄을 잠깐 바꿨다가 되돌리는 것 ② 승인된 개발 도구 설치로 바뀌는 패키지 파일(package.json·lock 등) ③ 승인된 기준선 계획 ⑥에 적힌 테스트 설정 파일.
2. **실제로 돈·메시지·외부 요청이 나가면 안 된다.** 바깥 호출은 전부 가짜로.
3. **실존 개인정보 금지.** 합성 데이터만(이름 "테스트고객", 전화 010-0000-0000, 메일 test@example.com). 운영 데이터를 복사하지 않는다.
4. **흔들리는 값 고정**: 현재 시각(한국시간 고정), 난수, 자동 번호, 정렬 순서.
5. **검증 우회 금지**: 기대값을 느슨하게 하거나 skip을 쓰지 않는다.
6. **실행 전 확인**: 명령 정의에 배포·DB 쓰기·외부 전송이 섞였거나 설정이 운영을 가리키면 실행하지 말고 묻는다(`gate: ask-user`). 모든 실행은 안전 실행기로 한다: `bash "${CLAUDE_SKILL_DIR}/../../hooks/run.sh" refactor-safe-run -- <명령>`. 첫 실행 결과에 운영 주소로 접속한 흔적이 보이면(예: 운영 도메인 이름) 즉시 멈추고 보고한다. `127.0.0.1:9` 연결 실패는 안전 실행기가 막은 것이니 정상이다 — 그 테스트는 "개발용 DB 필요"로 적는다.
7. 실행하지 못한 테스트는 "실행 불가"로 적는다. commit·push는 하지 않는다.

### 순서
1. (승인된 경우) 개발 도구 설치.
2. 기존 테스트 1회 실행(안전 실행기로) → 통과/실패 개수 기록(실패는 고치지 않고 목록만. `127.0.0.1:9` 연결 실패는 "개발용 DB 필요"로 따로 센다).
3. 기준선 하나씩: 만들기 → 실행 → 초록 확인 → 껍데기 확인 → 원복 확인 → 다음.
   - 껍데기 확인: 먼저 `git diff --name-only`로 지금 바뀐 기존 파일 목록을 적어 둔다(승인된 패키지·설정 파일만 있어야 한다). 소스 한 줄을 잠깐 바꿔 테스트가 빨강이 되는지 보고, 되돌릴 때 `git checkout`·`git restore`·`git stash`를 쓰지 말고 **그 줄을 직접 원래대로 고친 뒤** `git diff --name-only`가 적어 둔 목록과 같은지 확인한다. 빨강이 안 되면 그 테스트는 아무것도 지키지 않는 껍데기다 — 다시 만든다.
4. BASELINE.md 맨 끝에 `## 결과` 제목을 달고 그 **아래**에 결과 부분을 더한다(제목 없이 쓰거나 계획 부분을 고치면 승인이 풀린다):
   - `| ID | 무엇을 고정 | 파일 | 결과 | 껍데기 확인 |`
   - 의심 동작(버그 후보 — 고치지 않음) `| ID | 위치 | 지금 동작 | 왜 의심스러운가 | 사람이 판단할 것 |`
   - 아직 못 찍은 곳(위험), 성능 기준치(했다면), **한 줄 실행법**(사람이 직접 돌릴 명령)
5. `git status`로 확인: 바뀐 기존 파일은 승인된 패키지·설정 파일뿐이고, 새 파일은 `tests/baseline/`·`docs/refactor/`·승인된 설정 파일뿐이어야 한다. 아니면 멈추고 보고.
6. STATE: `phase: PLAN`, `gate: ask-user`, "대기 중인 결정·질문"에 "기준선 커밋", next: "기준선 커밋 후 /refactor:go". 사람에게 **지금 커밋해 달라고** 한 줄로 부탁하고 **여기서 멈춘다**(예: 터미널에서 `git add -A && git commit -m "test: 기준선 테스트 추가"` (CLI 라면 입력창에 `! git add …` 도 됨)). 기준선이 커밋돼야 안전장치가 기준선 파일을 지킬 수 있고, 단계 실행도 시작할 수 있다. 사람이 커밋하고 `/refactor:go`를 입력하면 `git status --porcelain -- tests`로 커밋을 확인한 뒤 6단계(계획서)를 시작한다.

> 참고: 이 단계가 끝나고 커밋되면 `tests/baseline/`의 파일은 안전장치가 보호한다(스냅숏 갱신 옵션·포맷터 포함). 나중에 동작을 일부러 바꾸는 단계에서 기준선을 새 동작으로 바꿔야 하면, 사람이 허용 파일을 만들어야 한다(7단계 참고). 단계 실행 중에 새로 만드는 테스트는 `tests/baseline/` 밖, 테스트 실행기가 이미 모으는 폴더(기존 테스트 옆)에 둔다 — 실행기 설정 밖 폴더에 두면 조용히 안 돌아간다(7단계 참고).
