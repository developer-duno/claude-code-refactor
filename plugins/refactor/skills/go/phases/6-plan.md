# 6단계: 계획서·승인서 (PLAN → ⏸ G2)

목표: 진단 결과로 **무엇을, 왜, 어떤 순서로, 얼마의 위험으로** 고칠지 적은 공사 계획서 `docs/refactor/REFACTOR_PLAN.md`를 만든다. 사용자는 단계마다 승인만 고른다. 이 단계에서는 코드를 한 줄도 고치지 않는다.

## 규칙
1. **근거 문서로만 계획한다**: PROJECT_MAP, AUDIT_REPORT, AUDIT_VERIFY, audit/*.md(특히 "계획서 후보"), BASELINE, PROFILE. 여기 없는 작업을 지어내지 않는다. 검증에서 "오류"로 판정된 항목은 넣지 않고 제외 목록에 적는다.
2. **작게 쪼갠다**: 한 단계 = 한 목적 = 되돌릴 수 있는 크기. 한 단계에서 바꾸는 파일은 되도록 3개 이하.
3. **두 종류를 섞지 않는다**:
   - 🔧 리팩토링 = 동작은 같고 모양만 바뀜. 기준선이 **그대로** 통과해야 완료.
   - 🛠 개선 = 동작이 바뀜(보안 구멍 막기, 결제 검증, 알림 추가, 법규 표시 등). 바뀌는 동작(전 → 후)과 **깨질 것으로 예상되는 기준선 목록**을 적는다.
4. **순서 규칙** (점수보다 먼저):
   - Phase 0 안전망: 원격 백업(Git)·DB 백업 확인, 기준선 통과 확인, AI 규칙 파일(CLAUDE.md 등) 정비 — 도메인 불변 규칙(예: 결제 금액은 서버에서 다시 계산, 같은 주문은 한 번만 처리)과 "기준선 테스트는 승인 없이 고치지 않는다" 포함, 200줄 미만
     - PROFILE에 운영/개발 DB가 "하나뿐" 또는 "모름"이거나 결제·알림 테스트 키가 없으면: **개발용 DB·테스트 키 준비**를 Phase 0 첫 단계로 넣는다(👤 사람이 할 일: 개발용 DB 만들기, 결제사·알림톡 테스트 키 발급, `.env`를 개발용 값으로 바꾸기). 이 단계가 끝나기 전에는 DB·외부 API를 쓰는 단계의 검증을 "실행 불가"로 적는다.
   - Phase 1 급한 구멍(🔴): 접근 권한·비밀값·결제 검증·백업·알림·법규 표시
   - Phase 2 안정화: 에러 처리·타임아웃·재시도·중복 방지, 개발/운영 분리, 의존성 보안 패치, 배포 되돌리기
   - Phase 3 품질·성장: 데이터 정합성, 성능, 검색 노출, 모바일·접근성
   - Phase 4 체질 개선: 구조 정리, 확장성, 비용
   같은 Phase 안에서는 위험이 낮은 것부터. 큰 공사는 새 것을 옆에 만들어 조금씩 옮긴다(스트랭글러 방식).
   - **실행 순서 = 의존 관계 > Phase > 우선 점수.** 앞 카드가 끝나야 하는 카드(`사전 조건` 에 `[P1-1]` 꼴로 적은 것)는 그 뒤에 둔다. Phase 0(안전망) 카드는 묶음이든 아니든 **맨 앞**. 묶음(아래 「묶음」)의 자리는 그 안 가장 급한 카드의 Phase. 묶음 없는 카드도 **Phase 순서 안에** 끼운다(맨 뒤로 밀지 않는다). 카드는 계획서에 이 순서대로 적는다 — 현황(`/refactor:status`)의 ▶ 실행 대기는 Phase 순서로 묶음을 모으고, 같은 Phase 안·묶음 안에서는 계획서에 적은 순서를 따른다.
5. **민감 구역**(결제·인증·권한·DB 구조·개인정보·법적 문구·운영 설정)을 건드리는 단계에는 "👤 사람 확인 필요"를 붙이고, 테스트 키·로컬(또는 스테이징 = 운영과 똑같이 꾸민 연습용 서버)에서 먼저 검증하게 적는다. 법적 문구는 "원문·전문가 확인 후 게시".
6. 시간은 범위로(예: AI 30분~1시간 + 사장님 확인 10분). 모르면 모른다.
7. **승인 칸은 비워 둔다.** `[ ] 승인`은 사용자가 `/refactor:approve`로만 바꾸고, 승인은 그 명령이 남긴 기록(APPROVALS.log)으로만 인정된다. 단계 ID는 겹치지 않게 한다(같은 ID가 둘이면 승인할 수 없다). 카드를 코드 블록(```) 안에 넣지 않는다. 카드 안에 작은 제목이 필요하면 `####`를 쓰고(카드의 일부로 본다), 카드 뒤의 다른 내용(다른 곳으로 넘길 것·보류 목록 등)은 반드시 `##` 제목으로 시작한다.
8. 이미 계획서가 있으면 새로 짜지 않는다. 완료 상태와 새 발견만 갱신 제안한다. **승인된 카드의 내용은 고치지 않는다** — 고치면 승인이 풀린다. 바꿀 것이 있으면 새 카드(새 ID)로 제안한다. 예외는 꼴에 맞는 `묶음`·`우선` 두 줄뿐이다(아래 「묶기만」).

## 같은 Phase 안의 순서 점수
우선 점수 = (심각도 × 사업 영향 × 확신도) ÷ (수정 난이도 × 변경 위험). 심각도·영향·난이도·위험은 1~5, 확신도는 확인됨 1.0 / 가능성 높음 0.8 / 추정 0.5.
그리고 4칸으로 나눈다: 빠른 승리(효과 큼·위험 작음) / 계획된 큰 공사(효과 큼·위험 큼) / 틈날 때 / 하지 말 것(이유와 함께 보류).

## REFACTOR_PLAN.md 형식
1. 한 줄 요약 (비유: "문부터 잠그고 → 소화기를 달고 → 인테리어")
2. 4칸 매트릭스 (칸마다 단계 ID)
3. Phase별 단계 목록 (한 줄씩: ID · 제목 · 🔧/🛠 · 위험도)
3-1. `## 묶음` 표 (Phase별 목록 뒤·카드 앞 — 아래 「묶음」): `| 묶음 | 설명 | 우선 | 카드 | 왜 함께 |`
4. 단계 카드 — 단계마다 **이 형식 그대로**(`/refactor:approve`와 실행 단계가 이 줄들을 읽는다):

```
### [P1-2] 제목
- **종류**: 🔧 리팩토링 / 🛠 개선(바뀌는 동작: 전 → 후)
- **묶음**: B1 결제 안전
- **우선**: 12.3 · 빠른 승리
- **무엇을**: (비개발자용 1~2문장)
- **왜**: (방치하면 생기는 사고 한 줄 + 근거 항목 코드)
- **건드릴 파일**: (백틱 경로 목록 — 예: `src/pay.ts:10-40`, `src/order.ts`)
- **건드리지 않을 것**:
- **사전 조건**: (앞 카드는 `[P1-1]` 꼴로 — 예: `[P1-1]` 완료, 기준선 BL-003 통과, DB 백업 확인)
- **검증**: (돌릴 기준선 ID, 새로 추가할 테스트, 사람이 화면에서 눌러볼 것)
- **깨질 것으로 예상되는 기준선**: (🛠만, 없으면 "없음". **프로젝트 폴더 기준 경로를 백틱으로** — 안전장치가 이 경로만 고치게 허락한다. 굵은 소제목·번호 목록은 칸을 끊으니 경로는 이 줄(또는 바로 아래 줄)에 이어 적는다)
- **되돌리는 법**: (이 단계에서 바꾼 파일만)
- **예상 시간**:
- **위험도**: 🔴🟠🟡🟢 + 이유
- **👤 사람이 직접 할 일**: (결제사 대시보드, 키 재발급, 법률 확인 등 / 없으면 "없음")
- **승인**: [ ] 승인
- **완료**: [ ] 완료
```

   - `묶음`·`우선` 두 칸은 **선택**이다(없어도 된다 — 아래 「묶음」). 넣을 때는 종류 칸 바로 다음에, **값을 이 꼴 그대로**: 묶음 = `B<숫자> <한글 설명>`(예: `B1 결제 안전` — 앞에 0 없이, 설명에 `|` 없이), 우선 = `<점수> · <4칸 이름>`(점수는 소수 한 자리까지, 4칸 이름은 `빠른 승리`·`계획된 큰 공사`·`틈날 때`·`하지 말 것` 중 하나 — 예: `12.3 · 빠른 승리`). 이 꼴의 두 줄은 승인 지문에 들어가지 않아 승인된 카드에도 덧붙이거나 바꿀 수 있다. **꼴이 다르면 보통 줄처럼 지문에 들어가** 승인 뒤에 바꾸면 "승인 뒤 카드 바뀜"이 된다. 칸 이름은 `묶음`·`우선` 그대로 쓴다(칸 이름에 `종류`·`위험도`·`사람이 직접 할 일` 낱말을 넣지 않는다 — 그 칸으로 읽힌다).

5. 다른 곳으로 넘길 것: 법률 전문가 확인 목록, 사람만 할 수 있는 일 목록
6. 보류·하지 말 것과 이유
7. 사장님께 물어볼 것(계획 확정에 꼭 필요한 것만, 최대 7개)

## 묶음 (함께 고칠 카드)
**묶음 = 함께 고칠 카드 몇 장 = 작업 가지 하나 = PR 하나.** 이름은 `B1`·`B2`(앞에 0 없이) + 한글 설명. 사용자는 `/refactor:approve B1` 한 번으로 그 묶음의 안 끝난 카드를 모두 승인한다.
- **묶는 규칙**(하나라도 맞으면 함께): ① 같은 파일·모듈을 건드림(`건드릴 파일` 의 백틱 경로가 겹침) ② 앞 카드에 의존함(`사전 조건` 의 `[P1-1]`) ③ 같은 영역·진단 항목(Phase 가 달라도 된다).
- **크기**: 한 묶음은 카드 5장·건드릴 파일 10개까지. 넘으면 `B2` 로 나눈다(`/refactor:approve` 도 안 끝난 카드가 5장을 넘는 묶음은 거절한다).
- 묶지 않는 카드가 있어도 된다(묶음 칸 없이 둔다) — 묶음 없는 카드끼리는 한 작업 가지에서 이어서 한다.
- `## 묶음` 표(Phase별 목록 뒤·카드 앞 — 카드 밖이라 지문에 안 들어가는 보기용): `| 묶음 | 설명 | 우선 | 카드 | 왜 함께 |`. 카드 칸에는 카드 ID 를 하나씩(`P1-1 P1-2` — 범위 `~` 로 줄이지 않는다), 완료 카드는 `P1-3(완료)`. 우선 칸은 그 안 가장 급한 카드의 우선 값. 표와 카드의 묶음 칸은 같게 적는다 — 승인 뒤 어느 쪽이든 승인 때와 달라지면 현황에 "⚠️ 묶음이 승인 때와 다릅니다 — 다시 /refactor:approve B1" 이 나온다.

### 묶기만 (`/refactor:go 묶음` — 진행 중인 계획서)
이미 계획서가 있고(승인·완료된 카드가 있어도) 묶음이 없을 때 쓰는 차례다. 이 차례에는 코드를 고치지 않는다(안전장치도 이 차례의 코드 수정을 막는다).
1. `## 묶음` 표가 없으면 카드(완료 포함)를 읽어 위 규칙으로 묶음을 제안한다. 이미 있으면 다시 묶지 않고 지금 묶음을 보고한다(바꿀 것이 있으면 사용자에게 묻고 바꾼다).
2. 카드에는 **`묶음`·`우선` 두 줄만** 종류 칸 바로 다음에 더한다 — 다른 줄은 한 글자도 바꾸지 않는다(승인된 카드가 풀리지 않는 것은 위 꼴 그대로인 두 줄뿐이다).
3. `## 묶음` 표를 Phase별 목록 뒤·카드 앞에 넣는다. 완료 카드는 표에 `(완료)` 를 붙인다.
4. 코드·승인 칸·완료 칸·승인 기록(`APPROVALS.log`)은 건드리지 않는다.
5. 보고: 묶음 표 요약 + 안내 — 승인은 `/refactor:approve B1`(그 묶음의 안 끝난 카드 전부) · 자동 모드는 `/refactor:approve B1 자동`.

인자 없는 `/refactor:go` 로 계획서 뒤(승인·실행 단계)에 들어왔는데 계획서에 `## 묶음` 표가 없으면, 진행하기 전에 한 줄로 `/refactor:go 묶음` 을 제안한다(강제 아님 — 그대로 진행해도 된다).

## 끝나면
- STATE: `steps_total` 기록, `phase: PLAN`, `gate: G2-plan`, next: "계획서 확인 후 /refactor:approve <단계ID…>".
- 보고에 Phase 0·1 단계 목록을 한 줄씩 보여 주고, 승인 예시를 준다: `/refactor:approve P0-1 P1-1 P1-2`(묶음을 만들었으면 `/refactor:approve B1`)
- **여기서 멈춘다.**
