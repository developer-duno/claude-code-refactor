# 6단계: 계획서·승인서 (PLAN → ⏸ G2)

목표: 진단 결과로 **무엇을, 왜, 어떤 순서로, 얼마의 위험으로** 고칠지 적은 공사 계획서 `docs/refactor/REFACTOR_PLAN.md`를 만든다. 사용자는 단계마다 승인만 고른다. 이 단계에서는 코드를 한 줄도 고치지 않는다.

## 규칙
1. **근거 문서로만 계획한다**: PROJECT_MAP, AUDIT_REPORT, AUDIT_VERIFY, audit/*.md(특히 "계획서 후보"), BASELINE, PROFILE. 여기 없는 작업을 지어내지 않는다. 검증에서 "오류"로 판정된 항목은 넣지 않고 제외 목록에 적는다.
2. **작게 쪼갠다**: 한 단계 = 한 목적 = 되돌릴 수 있는 크기. 한 단계에서 바꾸는 파일은 되도록 3개 이하.
3. **두 종류를 섞지 않는다**:
   - 🔧 리팩토링 = 동작은 같고 모양만 바뀜. 기준선이 **그대로** 통과해야 완료.
   - 🛠 개선 = 동작이 바뀜(보안 구멍 막기, 결제 검증, 알림 추가, 법규 표시 등). 바뀌는 동작(전 → 후)과 **깨질 것으로 예상되는 기준선 목록**을 적는다.
4. **순서 규칙** (점수보다 먼저):
   - Phase 0 안전망: 원격 백업(Git)·DB 백업 확인, 기준선 통과 확인, AI 규칙 파일(CLAUDE.md 등) 정비 — 도메인 불변 규칙(예: 결제 금액은 서버에서 다시 계산, 같은 주문은 한 번만 처리)과 "기준선 테스트는 승인 없이 고치지 않는다" 포함, 200줄 미만
     - PROFILE에 운영/개발 DB가 "하나뿐" 또는 "모름"이거나 결제·알림 테스트 키가 없으면: **개발용 DB·테스트 키 준비**를 Phase 0 첫 단계로 넣는다(👤 사람이 할 일: 개발용 DB 만들기, 결제사·알림톡 테스트 키 발급, `.env`를 개발용 값으로 바꾸기). 이 단계가 끝나기 전에는 DB·외부 API를 쓰는 단계의 검증을 "실행 불가"로 적는다.
   - Phase 1 급한 구멍(🔴): 접근 권한·비밀값·결제 검증·백업·알림·법규 표시
   - Phase 2 안정화: 에러 처리·타임아웃·재시도·중복 방지, 개발/운영 분리, 의존성 보안 패치, 배포 되돌리기
   - Phase 3 품질·성장: 데이터 정합성, 성능, 검색 노출, 모바일·접근성
   - Phase 4 체질 개선: 구조 정리, 확장성, 비용
   같은 Phase 안에서는 위험이 낮은 것부터. 큰 공사는 새 것을 옆에 만들어 조금씩 옮긴다(스트랭글러 방식).
5. **민감 구역**(결제·인증·권한·DB 구조·개인정보·법적 문구·운영 설정)을 건드리는 단계에는 "👤 사람 확인 필요"를 붙이고, 테스트 키·로컬(또는 스테이징 = 운영과 똑같이 꾸민 연습용 서버)에서 먼저 검증하게 적는다. 법적 문구는 "원문·전문가 확인 후 게시".
6. 시간은 범위로(예: AI 30분~1시간 + 사장님 확인 10분). 모르면 모른다.
7. **승인 칸은 비워 둔다.** `[ ] 승인`은 사용자가 `/refactor:approve`로만 바꾸고, 승인은 그 명령이 남긴 기록(APPROVALS.log)으로만 인정된다. 단계 ID는 겹치지 않게 한다(같은 ID가 둘이면 승인할 수 없다). 카드를 코드 블록(```) 안에 넣지 않는다. 카드 안에 작은 제목이 필요하면 `####`를 쓰고(카드의 일부로 본다), 카드 뒤의 다른 내용(다른 곳으로 넘길 것·보류 목록 등)은 반드시 `##` 제목으로 시작한다.
8. 이미 계획서가 있으면 새로 짜지 않는다. 완료 상태와 새 발견만 갱신 제안한다. **승인된 카드의 내용은 고치지 않는다** — 고치면 승인이 풀린다. 바꿀 것이 있으면 새 카드(새 ID)로 제안한다.

## 같은 Phase 안의 순서 점수
우선 점수 = (심각도 × 사업 영향 × 확신도) ÷ (수정 난이도 × 변경 위험). 심각도·영향·난이도·위험은 1~5, 확신도는 확인됨 1.0 / 가능성 높음 0.8 / 추정 0.5.
그리고 4칸으로 나눈다: 빠른 승리(효과 큼·위험 작음) / 계획된 큰 공사(효과 큼·위험 큼) / 틈날 때 / 하지 말 것(이유와 함께 보류).

## REFACTOR_PLAN.md 형식
1. 한 줄 요약 (비유: "문부터 잠그고 → 소화기를 달고 → 인테리어")
2. 4칸 매트릭스 (칸마다 단계 ID)
3. Phase별 단계 목록 (한 줄씩: ID · 제목 · 🔧/🛠 · 위험도)
4. 단계 카드 — 단계마다 **이 형식 그대로**(`/refactor:approve`와 실행 단계가 이 줄들을 읽는다):

```
### [P1-2] 제목
- **종류**: 🔧 리팩토링 / 🛠 개선(바뀌는 동작: 전 → 후)
- **무엇을**: (비개발자용 1~2문장)
- **왜**: (방치하면 생기는 사고 한 줄 + 근거 항목 코드)
- **건드릴 파일**: (파일:줄 — 목록)
- **건드리지 않을 것**:
- **사전 조건**: (예: 기준선 BL-003 통과, DB 백업 확인)
- **검증**: (돌릴 기준선 ID, 새로 추가할 테스트, 사람이 화면에서 눌러볼 것)
- **깨질 것으로 예상되는 기준선**: (🛠만, 없으면 "없음")
- **되돌리는 법**: (이 단계에서 바꾼 파일만)
- **예상 시간**:
- **위험도**: 🔴🟠🟡🟢 + 이유
- **👤 사람이 직접 할 일**: (결제사 대시보드, 키 재발급, 법률 확인 등 / 없으면 "없음")
- **승인**: [ ] 승인
- **완료**: [ ] 완료
```

5. 다른 곳으로 넘길 것: 법률 전문가 확인 목록, 사람만 할 수 있는 일 목록
6. 보류·하지 말 것과 이유
7. 사장님께 물어볼 것(계획 확정에 꼭 필요한 것만, 최대 7개)

## 끝나면
- STATE: `steps_total` 기록, `phase: PLAN`, `gate: G2-plan`, next: "계획서 확인 후 /refactor:approve <단계ID…>".
- 보고에 Phase 0·1 단계 목록을 한 줄씩 보여 주고, 승인 예시를 준다: `/refactor:approve P0-1 P1-1 P1-2`
- **여기서 멈춘다.**
